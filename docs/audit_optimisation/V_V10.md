## 1. ISO-01 — la lightmap `1080p` ne descend jamais sous 1920×1080

### 1.1 Le code (relu, exact)

`presentation_3d.gd:932-953` :
```gdscript
static func taille_lightmap(variante: String, logique: Vector2i, etirement: float) -> Vector2i:
	if variante == "plein":
		return Vector2i((Vector2(logique) * etirement).round())
	return logique
…
func _etirement() -> float:                       # hauteur de fenêtre / hauteur logique, AXE VERTICAL SEUL
	var aire := get_viewport().get_visible_rect().size
	var fenetre := DisplayServer.window_get_size()
	if aire.y <= 0.0 or fenetre.y <= 0:           # headless : window_get_size() rend 0 → étirement 1
		return 1.0
	return float(fenetre.y) / aire.y
```
`presentation_3d.gd:992-1007` (`_poser_lightmap`) — **`1080p`** : le conteneur garde `stretch = true`, donc la sous-vue prend la taille du conteneur
**en unités logiques** (`cadre.size.round()` : 1920×1080 en vue unique, 957×1080 et 958×1080 en scindé, `_cadre` `:960-973`) ; **`plein`** :
`stretch = false`, `top_level = true`, `vue.size = round(logique × e)` ; dans les deux cas `size_2d_override = logique` et `size_2d_override_stretch = true`.
La lecture côté 3D passe par `uv = (canevas × px + origine) / taille_N` avec **`taille_N = size_2d_override`** (`presentation_3d.gd:817-824`,
`iso_lightmap.gdshaderinc:52-59`) : **la texture peut changer de taille sans que l'aire logique, donc le champ, ne bouge**.

Fenêtre par défaut, **PROUVÉE** : `project.godot:72-76` — `viewport_width/height = 1920×1080`, `window_width_override/height_override = 1280×720`,
`stretch/mode = "canvas_items"` (`aspect` absent : `keep`, le défaut du moteur et la décision du 2026-08-25, l. 2555). `settings_manager.gd:293-298` :
**hors build de débogage**, `_apply_resolution()` n'est appelée que si un choix a été enregistré → une installation neuve reste à **1280×720 pixels** ;
en débogage `_apply_windowed` double (`:815`, `DEBUG_WINDOW_FACTOR = 2`) puis borne à la zone utile de l'écran (`:819-823`) — c'est pourquoi tous les relevés Mac
(l. 24368 « fenêtre 2560×1440 (étirement ×1,33) ») sont à `e = 1,333` et ne disent rien d'une fenêtre par défaut. Trois choix de résolution seulement :
« FENÊTRÉ 1280 », « FENÊTRÉ 1920 », « PLEIN ÉCRAN » (`ui.gd:7813`).

### 1.2 La fréquence, les appelants

`Presentation3D._process` (chaque image, `:495-523`) → `_tenir()` (`:724-739`, relit `_lightmap_en_place(vue)` `:1012-1022`, donc `_etirement()`, **déjà chaque image**) →
`_poser_lightmap(vue)` seulement si l'écart est constaté (+ une fois à `_allumer()`, `:619`). Le COÛT, lui, est payé **chaque image rendue** tant que la vue iso tient :
la vue regardée est en `UPDATE_ALWAYS` (`game_state.gd:5922-5924`). Vue unique : 1 lightmap ; écran scindé : 2 (957+958 px de large, même total de pixels).
Rien de ceci n'existe en `--2d` ni sous les menus (iso éteinte). **Aucune lecture CPU de la texture** : `grep get_image` ne trouve aucun appel sur `vp1/vp2.get_texture()`
dans le code de jeu (arena_decor, exporteur, charte, iso_nuage_voxel, menu_icones, weapon_data lisent leurs propres images) ; le bot lit `enabled` des lumières
(`perception_bot_noeud.gd:316`), jamais un pixel.

### 1.3 Ce qu'est la « densité » à l'écran (recalculée)

Densité = texels de lightmap par pixel d'écran. Verticale : `1080 / H` (c'est `Presentation3D.texels_par_pixel`, F3, `:1857`, et le « 0,75 » de la l. 26284-26287 à 1440 px).
Horizontale : la caméra iso ne lit que `1920 × sin 52° = 1513` colonnes (`camera_iso.gd:93-101`, `test_iso_camera.gd:86-88`), soit `1513 / W`. **Le zoom n'y change rien**
(la lightmap rend le monde déjà zoomé, à taille de texture constante : l. 26284 ; vérifié : le zoom est dans `canevas`, pas dans la taille).

| Fenêtre | `1080p` (actuel) | `min(logique, fenêtre)` (auditeur = `plein` quand e < 1) | Dens. `1080p` H / V | Dens. `min` H / V |
|---|---|---|---|---|
| 1280×720 (défaut d'un build publié) | 2,07 Mpx | 0,92 Mpx (**−55,6 %**) | 1,18 / 1,50 | **0,79 / 1,00** |
| 1366×768 | 2,07 | 1,05 (−49,4 %) | 1,11 / 1,41 | 0,79 / 1,00 |
| 1600×900 | 2,07 | 1,44 (−30,6 %) | 0,95 / 1,20 | 0,79 / 1,00 |
| **1920×1080** | 2,07 | 2,07 (0) | **0,79 / 1,00** | 0,79 / 1,00 |
| 2560×1440 (Mac d'Adrien, débogage) | 2,07 | 2,07 (0) | 0,59 / 0,75 | inchangée |
| 3840×2160 | 2,07 | 2,07 (0) | 0,39 / 0,50 | inchangée |

**Fait que le rapport source ne dit pas, et qui pèse sur le risque visuel** : sous `min`, toute fenêtre ≤ 1080p reçoit **exactement la densité qu'a aujourd'hui un joueur en 1920×1080**
(0,79 horizontal / 1,00 vertical) — le plein écran le plus répandu —, et reste **plus fine** que celle de la fenêtre d'Adrien (0,59 / 0,75, jugée « propre » : l. 26849). Le rapport écrit
« de 1,2 / 1,5 à 0,8 / 1,0 » comme un risque ; c'est en réalité un **alignement** sur un rendu déjà livré. Autres écarts de chiffres du rapport : « 0,44 pixel d'écran par texel » vaut sur la
lightmap entière ; sur la bande lue c'est 0,56 ; « sans bénéfice visuel » est trop fort — le gain de netteté d'une lightmap suréchantillonnée est faible et **non mesuré**, pas nul
(filtre linéaire sans mipmap : `iso_lightmap.gdshaderinc:28,35`, donc du crénelage de minification à 1,5 texel/px, ce que `min` retire).

### 1.5 Le coût

- **PROUVÉ** : l'arithmétique du tableau ; `1080p` = 1920×1080 quelle que soit la fenêtre (mesuré aussi à quatre tailles de fenêtre de 1280×720 à 3840×2160, l. 7407-7420, sur le même conteneur `stretch`) ; les appels de dessin ne changent pas
  (`plein` contre `1080p` : « 3 de plus, 6 de moins : le bruit », l. 24382-24385) — **le seul compteur indépendant du matériel est donc le nombre de pixels**, que `bench_framerate._conditions()` imprime déjà
  (`tools/bench_framerate.gd:1171-1205`, « Pixels de jeu » et « vp1 : rendu W×H ») et F3 (`presentation_3d.gd:1827-1852`).
- **Mécanisme** (sources 4.7.1) : les lumières d'un item sont rassemblées **par item** (`rasterizer_canvas_gles3.cpp:836-871` : `light_count`, `lights[4]`, plafond `max_lights_per_item`, empaquetés dans les drapeaux d'instance ;
  un item entre dans la liste si son rectangle global coupe celui de la lumière) et évaluées **par fragment** par le shader canevas (non relu ici) : le coût d'éclairage croît avec les fragments de la cible, donc avec ses pixels.
  Le « carré de 936 px » du rapport (§ 4 q. 3) n'est donc pas un quad que la lumière dessine : c'est le rectangle qui décide quels items reçoivent la lumière, et chaque item reçu paie la boucle de lumières sur TOUS ses fragments (l'ordre de grandeur de surface du rapport tient, la mécanique est différente). Sur un GPU lié au remplissage la passe suit donc les pixels.
- **ESTIMÉ, très incertain** : l'auditeur dit « 1 à 2 ms sur GPU intégré ou modeste ». C'est 55 % de **3,65 ms** (l. 24387 : « les torches coûtaient 3,65 ms par image au relevé du 2026-09-14 ») — chiffre
  **antérieur à l'allègement de la 0.8.0 et à Q76 (portée 468 px)**, d'une configuration que la ROADMAP ne documente pas, et la proportionnalité aux pixels n'est pas vérifiée. Le seul contre-indice mesuré
  va dans l'autre sens **sur le Mac** : +15 % de cadence pour ×3,6 de pixels quand on a supprimé la cible intermédiaire (l. 17192-17199 ; torches éteintes, donc non transposable aux lampes allumées). **Aucune mesure, nulle part, du
  temps de la passe lightmap en fonction de sa taille** (les cinq relevés de H-ISO5 ne sont jamais pris, l. 25305-25312). Ma lecture : plausible sur GPU lié au remplissage (peut dépasser 2 ms sur un GPU intégré ancien),
  **inexistant** là où le fil principal borne l'image (CPU 1,9 à 11,4 ms mesurés sans rendu : `00_M_mesures.md` § 4) — **À MESURER**, et la cible n'est pas le Mac.
- **Nul sur la machine de référence** (PROUVÉ : `min(1920×1080, 2560×1440) = 1920×1080`) : la seule personne qui teste ne verra donc aucune différence, ce qui est une raison de plus de ne pas décider sans donnée de testeurs.

### 1.6 Les invariants (la question posée)

**La lightmap est-elle « la seule vérité d'équité » ? Plus petite chez l'un, change-t-elle ce qu'il voit ?** Ligne par ligne :

| Quoi | Dépend de la taille de la texture ? | Preuve |
|---|---|---|
| Quelles lumières chaque joueur a le droit de voir (halo de proximité propre, masques `~4` / `~2`, canaux) | **Non** | `iso_lightmap.gdshaderinc:1-26`, `_accorder_rendu_aux_vues`, `test_iso_vues` (« aucun CanvasItem que lit la lightmap de J1 ne reçoit le canal de J2 ») |
| Le champ (ce que la 3D peut montrer, le « noir hors du rectangle couvert ») | **Non** | UV = `/ size_2d_override` ; `get_visible_rect()` = `size_2d_override` quand il est posé (le dépôt l'emploie ainsi : `presentation_3d.gd:1847` le lit comme aire logique à côté de `vue.size`, la taille de texture), donc `RegardDuel`, killcam, `PorteeEcran` (constantes `VUE_UNIQUE`, `portee_ecran.gd:32`) ne bougent pas |
| L'éblouissement (mécanique de jeu : pénalité de vitesse) | **Non** | `eblouissement.gd:160-169` échantillonne le **cookie** de la source côté CPU ; rien ne relit la lightmap |
| Simulation, réseau, RPC, déterminisme | **Non** | aucun `get_image()` sur les sous-vues ; rendu local |
| Seuils de lumière : point noir 2D (`seuil_noir_2d` = 8/255), niveaux de la pâte D (e1 = 0,02 + 0,03b, e2 = 0,16 + 0,08b, e3 = 0,42 + 0,1b, OMBRES O3), pochoir | **Sur des VALEURS échantillonnées** : le contour d'un seuil se déplace d'au plus ½ texel (≈ 0,5 px de monde à 1,0 texel/px) | `iso_lightmap.gdshaderinc:59-68,74-90` ; **non prouvable par lecture** — se tranche par comparaison d'images au même instant (banc) |
| Bords d'ombre | **Non** (la géométrie des marches est celle de l'atlas d'ombres, OMBRES O4 : `SHADOW_FILTER_NONE`, ≈ 512 texels/quart de tour) ; la lightmap ne fait que les rééchantillonner | `ROADMAP_branche_OMBRES.md` l. 33938 (O4) ; pâte D : l. 33937 (O3) |
| Visibilité des volumes (fumée, rayon) : « le noir gagne » | **Même nature que les seuils** : `ecran_noir` / `montre_noir` jugent des valeurs lues avec des décalages en pixels de MONDE (±3 px, (3 ; 2), rayon `0,18 × rayon`) | `iso_lightmap.gdshaderinc:45,83-88`, `volume_iso.gdshader:80,117-124` |

Conclusion : **aucune atteinte démontrable à l'équité au sens du projet**. Le projet range la **netteté hors de l'équité** — R5 (2026-08-25, l. 17247-17252) : « La netteté ne change aucune information de jeu … en faire une option ne crée pas
d'inégalité, contrairement au champ de vision » —, et la taille de lightmap est **déjà** un réglage par joueur (§ 1.4) : deux joueurs d'un même match ont déjà, par construction, des lightmaps de tailles différentes. Les effets du Monde, eux, ne se
règlent pas (`effect_policy.gd:19-35`, décision du 2026-09-12), mais la résolution n'en est pas un. **Ce qui reste, et qui est bien une décision d'Adrien :**

1. **La netteté des surfaces qui portent la lumière.** DA2 (l. 17274-17279, « reste à faire valider par Adrien ») : « Sous-échantillonner ne se règle par rien … la netteté des surfaces qui portent cette lumière n'est pas un poste où l'on rogne ». À 0,79 texel/px
   horizontal, `min` est **sous 1** sur l'axe large (comme l'est déjà le 1080p plein écran). Un plancher cohérent avec ce cadre : **au moins 1 texel de lightmap par pixel de MONDE** (l'art des tuiles est cuit à 35 px pour une case de 35 unités, soit 1 texel par pixel de monde : l. 7429-7430, 7438-7439), soit une hauteur de lightmap
   ≥ `1080 / zoom` (720 à ×1,5 ; 864 à ×1,25). À ×1,5 (vue unique, constante en ligne) `plein` ne passe jamais dessous pour une fenêtre ≥ 1280×720 ; **en écran scindé (×1,25) il passe dessous sous 1536×864**.
2. **H13.** Sans machine nommée, ni le bénéfice ni le seuil ne sont définis.
3. **Le changement de sens d'un réglage persisté.** `1080p` est écrit dans `settings.cfg` à chaque sauvegarde de réglages (`settings_manager.gd:975`), donc chez tout joueur qui a touché un réglage : redéfinir `1080p` en « au plus la fenêtre » change le rendu de tous les joueurs ≤ 1080p sans qu'ils l'aient demandé ; `ConditionsDeMatch.iso_lightmap` (`conditions_de_match.gd:60,105`) continuerait d'écrire « 1080p » pour une cible de 1280×720, et F3 (`:1835`) de même — **le diagnostic mentirait**.

Autres points d'invariant, vérifiés :
- **Tests existants.** `test_iso_vues.gd:193-220` (`1080p` = `logique`, conteneurs en `stretch`) et `:412-414` (`taille_lightmap("1080p", 957×1080, 1,333) == 957×1080`) **restent verts** (e ≥ 1 ou headless) ; **aucun test ne couvre e < 1** et `_etirement()` lit `DisplayServer` en dur : il faut le rendre injectable pour tester `_poser_lightmap` à e < 1. `test_banc_iso.gd:114-118` teste **la copie du banc** (`tools/banc_iso.gd:2552`), qui divergerait du jeu. Le rapport cite « `test_banc` (tailles de lightmap) » : **inexact** — `test_banc.gd` n'a que des gardes de texte sur d'autres lignes de `presentation_3d.gd` (relief, lumière 3D) ; aucune ne porte sur `taille_lightmap` ni `_poser_lightmap`.
- **Bancs déterministes.** Inchangés tant que la fenêtre est ≥ 1920×1080 ou absente : cloud Xvfb 1920×1080 (`tools/cadence_cloud/prise.sh`, l. « -screen 0 1920x1080x24 »), headless. Les gardes d'OM0 comptent des pixels de lightmap à 1080p (`ROADMAP_branche_OMBRES.md` l. 34097 : « 1 351 à 2 696 pixels de lightmap au-delà de 8 niveaux ») : à lancer à ≥ 1080p ou avec un `1080p` exact.
- **Trappe de `BackBufferCopy`** (l. 16590-16625 : son `rect` est en texels de framebuffer) : cherchée et **non applicable** — le seul `BackBufferCopy` dans le canevas d'une sous-vue 2D est `KillcamBB` en `COPY_MODE_VIEWPORT` (`game_state.gd:635-640`) ; le brouillage (`COPY_MODE_RECT`) vit sous `parent_ecran`, dans la racine.
- **`_etirement()` ne lit que la hauteur** : en `keep`, l'échelle réelle est `min(w/1920, h/1080)` ; sur 16:10 (1280×800 : 0,741 au lieu de 0,667) le calcul actuel surdimensionne de 11 %. Un correctif qui garde `_etirement()` perd ce gain sur les portables 16:10.
- **Fenêtre redimensionnée / alt-tab** : chaque variation de `e` repose `vue.size` (réallocation de cible, `lightmaps_reposees`). Aujourd'hui `1080p` y est insensible ; sous `min`, la zone e ≈ 1 et une minimisation qui rendrait `window_get_size() = 0` (le garde `:951` renvoie alors 1,0) feraient osciller la taille. **À vérifier** avant tout automatisme ; et les transitions de focus sont déjà ce qui détruit le 1 % bas (l. 17034-17050).
- **Réseau, RPC, nommage** : sans objet (rendu local, aucun nœud ajouté).

### 1.7 Statut

**CONNU-OUVERT**, pas NOUVEAU : H15 (l. 23971), relevé de fin de chantier (l. 25268-25319, critère de la plus petite lightmap), l. 26284-26287, 26849, trois commentaires de code (§ 1.4). Seul est nouveau l'angle « borner par le haut à la fenêtre » —

### 1.8 Verdict, correctif minimal, preuve dans le cloud

**CONFIRMÉ AVEC RÉSERVE — MINEUR.** Le geste minimal n'est pas du code, c'est **la mesure, puis la question à Adrien** (H13 + « un 1080p-window-look sur toute fenêtre ≤ 1080p, oui ou non ? »). Si oui :
une **troisième valeur `auto`, NON défaut** (`LIGHTMAPS` et `LIGHTMAPS_ISO` : `ui.gd:7859` fabrique le bouton tout seul) — `taille_lightmap("auto", logique, e) = round(logique × min(e, 1))` avec plancher `≥ 1080/zoom` de hauteur, `_poser_lightmap` /
`_lightmap_en_place` traitant `auto` à e < 1 comme `plein`, `_etirement()` remplacé par `min(w/1920, h/1080)` et injectable, F3 et `ConditionsDeMatch` écrivant la **taille réelle**, un test `taille_lightmap` à e = 0,667 et un test de placement à e < 1. ## 2. ISO-02 — 21 % des colonnes de la lightmap ne sont jamais échantillonnées

### 2.1 Le code (exact) et le fait

`camera_iso.gd:93-101` : `empreinte_au_sol(tangage, vue) = Vector2(taille × vue.x / vue.y, taille / sin θ)` avec `taille = vue.y × sin θ` (`taille_orthographique`, `:93-95`) ; `Camera3D.keep_aspect = KEEP_HEIGHT` (`:35`). À 52° la largeur au sol est
`1920 × 0,78801 = 1512,98` px : **PROUVÉ** (arithmétique, et **épinglé par `test_iso_camera.gd:86-88`**, headless, indépendant du matériel). 1 − sin 52° = **21,199 %** (2 × 203,5 px logiques, quel que soit le zoom ; 754 sur 957 en scindé).
Le lecteur côté 3D passe par `lire_lightmap` (`iso_lightmap.gdshaderinc:52-69`) : tout fragment visible lit une colonne dont l'abscisse écran est la sienne — la hauteur ne déplace l'abscisse que verticalement, et la caméra 2D tourne de −L avec la caméra iso
(`GameState.orienter_camera_2d`, voie (b) d'ISO14) : le constat tient aussi au lacet 45° par défaut (`settings_manager.gd:186-189`). L'en-tête de `camera_iso.gd:1-18` dit encore « lacet 0° la valeur actée » : périmé, sans effet sur le fait.
Décision d'Adrien rappelée : la profondeur plutôt que la largeur (H15, l. 23969 ; l. 4662-4672 « une question d'équité de champ »).

### 2.2 Fréquence, coût

Chaque image iso (la lightmap est toujours rendue : `UPDATE_ALWAYS`, `game_state.gd:5922-5924`). Le moteur écarte un item dont le rectangle ne coupe pas celui de la vue (`renderer_canvas_cull.cpp:260`, `p_clip_rect.intersects(p_global_rect)`) et ne rastérise rien hors cible :
rogner la cible retire donc **les fragments** des bandes (sol, décor, LED, halos) et **les items entièrement dedans**. Les torches (carrés de ≈ 1404 px logiques) tiennent presque dans la bande : le gain y est ≤ 8 % (le rapport l'a bien vu).
**Le « ≤ 0,3 ms ESTIMÉ » ne repose sur rien** : borne haute théorique = 21 % (en pratique ≈ 15,6 %, § 2.3) de ce que la passe paie au remplissage — non mesuré, et **inexistant** si le fil principal borne l'image. **À MESURER.**

### 2.3 Le correctif proposé casse trois choses que le rapport ne chiffre pas

1. **La marge de ±16 px est trop courte.** Les lectures de lissage de la fumée vont à `0,18 × rayon` de monde (`volume_iso.gdshader:80,231` ; `nuage_voxel_iso.gdshader:133,435`), jusqu'à 36 px pour `RAYON_FUMEE = 200` (`fusee_modele.gd:108`), soit **54 px logiques à ×1,5**, 45 à ×1,25 et 108 au zoom maximal de débogage (×3). Une fumée au bord latéral lirait hors de la lightmap rognée → `vec3(0)` (`iso_lightmap.gdshaderinc:56-58`) dans la moyenne : **un assombrissement visible le long des bords**.
   La marge doit croître avec le zoom ; avec 2 × 54 px, le gain est **15,6 %** et non 19,5 %. Autres lectures latérales : `soi_fondu_rayon_px = 30`, `PIED_PX = 8`, ±3 px de pente, (3 ; 2).
2. **Le champ.** `size_2d_override` rogné change `get_visible_rect()` de la vue 2D, que lisent `game_state.gd:452` (`RegardDuel.centre_du_regard`, bornes de carte à une tuile de hors-carte : `regard_duel.gd:46-67`), `game_state.gd:2292` (cadrage de killcam), `player.gd:3142` (rectangle visible pour le bandeau fatal), `brouillage_vue.gd:259`.
   La caméra pourrait s'approcher d'environ **125-135 px de plus** des murs est/ouest (ΔL/2/zoom) : **une règle de champ**, et Adrien a posé l'équité de champ comme intangible (l. 2555 : « voir plus de carte parce qu'on possède un autre écran est une asymétrie que personne n'a payée »). Sans découplage (`RegardDuel` lisant une constante 1920×1080, comme `PorteeEcran.VUE_UNIQUE`), c'est une décision de jeu.
   (Les autres lecteurs de `get_visible_rect()` — `affiche_de_fin`, `estampe_de_kill`, `panneau_de_soiree`, `power_on`, `ui.gd` — interrogent **leur propre** viewport, la racine en iso : non concernés. Je n'ai pas vérifié `brouillage_vue.gd:259`.)
3. **Les tests.** `test_iso_vues.gd:193-194` (`vp1.size == logique and size_2d_override == logique`), `:211-220`, `:412-414`, `:531`, `:812` ; `test_iso_camera`/`test_iso_equite` (`RegardDuel` à `Vector2(1920, 1080)` en dur, `test_iso_equite.gd:50,188`) ; `banc_iso.gd`. À réécrire. La lightmap rognée n'est de plus utilisable qu'en iso (en `--2d` la sous-vue EST la vue).
   Aucun correctif « sans toucher à `size_2d_override` » ne retire les colonnes : un écrasement anamorphique (`vue.size` plus étroit, `size_2d_override` intact) garde les 21 % de fragments en les rendant plus grossiers — c'est le même compromis qu'ISO-01, pas un gain en plus.

**Interaction avec ISO-01** (que le rapport ne relie pas) : c'est ISO-02 qui fait que `plein` n'est qu'à 0,79 texel/px dans la bande ; la lightmap « idéale » à 1280×720 serait `(1280 + marge) × 720` à 1,0/1,0 pour ≈ 0,94-1,0 Mpx (−52 à −55 %, selon la marge) — mais elle exige ISO-02 en entier. Sans lui, la taille sans perte horizontale est 1625×914 (−28 %) ou, en anamorphique, 1625×720 (−44 %, **non évalué**).

### 2.4 Statut, verdict, preuve

**NOUVEAU** (aucune trace de « rogner la lightmap » dans la ROADMAP ni dans la branche OMBRES). Titulaire des fichiers : `presentation_3d.gd` est l'un des fichiers que l'audit et OMBRES visent (ROADMAP, section AO). **CONFIRMÉ AVEC RÉSERVE — MINEUR : ne pas faire** tant que la passe lightmap n'est pas mesurée liée au remplissage **et** qu'ISO-01 n'est pas tranché ;
si on le fait, découpler d'abord le regard (constante), puis une marge `≥ 0,18 × RAYON_FUMEE × zoom_max`. **Preuve cloud** : (a) arithmétique : `CameraIso.empreinte_au_sol(52, (1920,1080)).x = 1512,98` (déjà dans `test_iso_camera`) ; (b) compteur : pixels de cible 1920×1080 → (1920 − 2·marge)×1080 ;
(c) temps : arbre gelé par une retouche de `_poser_lightmap` (`size_2d_override` et `size` rognés), llvmpipe A B B A à 1920×1080 — **borne haute** ; (d) image : bandes d'écran de gauche et de droite avec une fumée posée au bord, à ×1,5 puis ×3.

## 3. ISO-03 — un parcours de tous les enfants de l'arène, à chaque image, pour retrouver l'onde de mort

### 3.1 Le code (exact)

`iso_volumes.gd:425-431` :
```gdscript
var arene := main.get("arena") as Node
if arene != null:
	for noeud in arene.get_children():
		if noeud.get_script() == OndeDeMort:
			_suivre_onde(noeud as Node2D, vus)
```

`OndeDeMort := preload("res://kill_shockwave.gd")` (`:43`). L'onde naît à `game_state.gd:4546-4549` (`KillShockwave.new()`, `arena.add_child(shock)`), vit `DURATION = 0.4` s puis `queue_free()` (`kill_shockwave.gd:27,74-79`).
**L'onde est le seul nœud cherché**, et le seul endroit du dépôt qui en crée une est ce `new()` (`grep`).

### 3.2 Fréquence, appelants remontés, quantité

`Presentation3D._process` (`:495`) → `_suivre()` (`:795`) → `_miroirs.suivre(...)` (`:915`) → `MiroirsIso.suivre` (`miroirs_iso.gd:147-175`, **appel inconditionnel** de `volumes.suivre(...)` en `:175`) → `IsoVolumes.suivre` (`iso_volumes.gd:409-447`, sorti tôt seulement si `images_actives` est faux : vrai par défaut).

Plafonds `MAX_CASINGS = 120` (`bullet_casing.gd:19`), `MAX_STAINS = 120` (`blood_stain.gd:37`), `MAX_ECLATS = 90` (`wall_impact.gd:45`) : 330 × 2 = **660** enfants à saturation, plus les empreintes (fondu de 2 s), flaques, gerbes et la dizaine d'enfants permanents (`game_state.gd:1468-1488`, `:640-647`). **Persistance d'une manche à l'autre** contre le même adversaire :
`_empreinte_de_la_rencontre` (`game_state.gd:1354-1371`, Q53). Mesuré par l'agent de mesure (`00_M_mesures.md` § 4.1) : plafond des traces **atteint vers 100 s** dans un duel contre le bot (989 groupes = 3 × 330 en iso, dont 660 enfants de l'arène), plat ensuite.

### 3.3 Le coût

PROUVÉ par lecture du code : O(n), n ≤ ≈ 700, une copie du tableau d'enfants (`get_children()` rend un `Array` neuf ; implémentation moteur non relue dans les sources fournies) puis un appel natif par nœud. **ESTIMÉ** : une itération typée + `get_script()` + comparaison d'objets ≈ 0,1-0,2 µs (contre 0,3-0,8 µs pour un `set_shader_parameter`
dans le barème de V2 § 0.2) → **≈ 0,07-0,14 ms à 700 enfants**, plus 10-20 µs pour le tableau : **0,05-0,15 ms**, ≈ 0,02-0,05 ms à mi-match. L'hypothèse « ≈ 0,25 µs par nœud » du rapport est le haut de ma fourchette, pas son centre. Soit 0,3 à 0,9 % du budget de 16,7 ms. Cohérent avec la pente globale mesurée
(« 1 à 2 µs par groupe de traces et par image », tous consommateurs confondus, non isolée, `00_M_mesures.md` § 4.1) : ISO-03 en est au plus un dixième. **À mesurer par micro-banc** (`audit/v10_work/micro_onde.gd`, écrit, **non lancé, non testé** ; µs par image à 0/100/300/700 enfants contre un groupe vide).
**Un A/B d'image entière ne le verrait pas** : le bruit entre deux prises identiques est de ±6 % (3,79 contre 4,26 ms, § 4) et `Performance.TIME_PROCESS` est un maximum par seconde (piège d'AO) — seul le micro-banc, ou `Time.get_ticks_usec()` autour de l'appel, a la résolution.

### 3.4 Invariants, tests, statut
